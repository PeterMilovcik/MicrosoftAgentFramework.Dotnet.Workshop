# Module 09 - Magentic Manager Orchestration

**Duration:** ~25 minutes  
**Goal:** Use the framework's built-in Magentic orchestration for adaptive planning, delegation, progress tracking, replanning, and human plan review.

> **Advanced / Bonus Module**: requires the core modules (00-06) and benefits from Modules 07-08.

---

## What's New in This Module

Module 09 uses `MagenticWorkflowBuilder` from `Microsoft.Agents.AI.Workflows` instead of implementing a manager loop by hand:

- A manager agent creates a task plan and dynamically selects participants.
- Progress ledgers help the manager detect stalls and decide when the request is satisfied.
- The manager can replan when work stops progressing.
- Generated plans pause at a real workflow checkpoint for human approval or revision.
- Framework events expose plans, progress, participant streaming, failures, and final output.

This is an architectural replacement for the old custom `ManagerDecision` protocol, not a class rename. The framework does not expose a public `MagenticManager` type. Its supported entry point is `MagenticWorkflowBuilder`.

## Team

| Agent | Responsibility | Tools |
|-------|----------------|-------|
| `magentic-manager` | Plans, delegates, tracks progress, and replans | No |
| `researcher` | Gathers evidence from logs and the knowledge base | `ReadFile`, `SearchKb`, `GetTime` |
| `diagnostician` | Ranks likely root-cause hypotheses | No |
| `critic` | Challenges claims and identifies evidence gaps | No |
| `scribe` | Drafts the evidence-based JSON `TriageCard` | No |

Only the researcher receives tools. Agent names and descriptions matter because the manager uses them when choosing the next participant.

## Workflow Controls

| Setting | Value | Purpose |
|---------|-------|---------|
| `RequirePlanSignoff` | `true` | Pause generated plans for human review |
| `WithMaxRounds` | 8 | Bound participant rounds |
| `WithMaxStalls` | 3 | Replan after repeated lack of progress |
| `WithMaxResets` | 2 | Bound full plan resets |
| Checkpoint store | In memory | Resume the paused run after plan review |

These controls replace the previous custom confidence threshold and tool-call counter. Tool use is naturally bounded by rounds, stalls, resets, model limits, and the tools assigned to each participant.

### Plan Signoff

`RequirePlanSignoff(true)` reviews the plan generated by the manager. This differs from asking for permission before the manager starts because the reviewer can inspect and revise a concrete plan.

At each plan review, enter one of:

- `approve`: continue with the proposed plan
- `revise <feedback>`: send feedback to the manager and review its revised plan
- `abort`: stop the run

Setting `RequirePlanSignoff(false)` allows plans and replans to proceed without human review. That can reduce interaction latency, but it removes this control point. Module 05 demonstrates how to build application-owned approval and tool-policy guards when a workflow needs different semantics.

## Core Builder

```csharp
Workflow workflow = new MagenticWorkflowBuilder(managerAgent)
    .AddParticipants([researcherAgent, diagnosticianAgent, criticAgent, scribeAgent])
    .WithName("Magentic Software Triage")
    .WithDescription("Coordinates evidence gathering, diagnosis, criticism, and structured triage output")
    .WithPromptOverrides(new MagenticPromptOverrides
    {
        FinalAnswerPrompt = MagenticDefaultPrompts.FinalAnswerPrompt +
            " Return only the latest valid JSON Triage Card drafted by the scribe.",
    })
    .RequirePlanSignoff(true)
    .WithMaxRounds(8)
    .WithMaxStalls(3)
    .WithMaxResets(2)
    .Build();
```

The manager is passed to the constructor. Specialists are added as participants. The manager has no tools and must delegate evidence gathering to the researcher. The final-answer override preserves the framework's default synthesis prompt while constraining its terminal answer to the required JSON contract.

## Checkpointed Plan Review

A plan-signoff request pauses the workflow. Module 09 watches without blocking on that request, captures the latest checkpoint, creates an approve or revise response, then resumes from the checkpoint:

```csharp
var checkpointManager = CheckpointManager.CreateInMemory();
var environment = InProcessExecution.Lockstep.WithCheckpointing(checkpointManager);

await using var run = await environment.OpenStreamingAsync(workflow);
await run.TrySendMessageAsync(messages);
await run.TrySendMessageAsync(new TurnToken(emitEvents: true));

await foreach (var evt in run.WatchStreamAsync(blockOnPendingRequest: false))
{
    if (evt is RequestInfoEvent requestEvent &&
        requestEvent.Request.Data.As<MagenticPlanReviewRequest>() is not null)
    {
        pendingRequest = requestEvent.Request;
    }

    if (evt is SuperStepCompletedEvent completed)
    {
        checkpoint = completed.CompletionInfo?.Checkpoint ?? checkpoint;
    }
}

var review = pendingRequest.Data.As<MagenticPlanReviewRequest>()!;
var response = pendingRequest.CreateResponse(review.Approve());

await using var resumed = await environment.ResumeStreamingAsync(workflow, checkpoint!);
await resumed.SendResponseAsync(response);
```

The same mechanism handles an initial plan and any later replan caused by a stall.

## Observable Events

The sample surfaces these framework events:

| Event | What the console shows |
|-------|------------------------|
| `MagenticPlanCreatedEvent` | Initial task ledger and plan |
| `MagenticReplannedEvent` | Replacement plan after a reset |
| `MagenticProgressLedgerUpdatedEvent` | Satisfaction, loop, progress, next speaker, and instruction |
| `AgentResponseUpdateEvent` | Streaming participant output |
| `RequestInfoEvent` | Generated-plan review request |
| `SuperStepCompletedEvent` | Resumable checkpoint |
| `WorkflowOutputEvent` | Final conversation transcript |
| `WorkflowErrorEvent` / `ExecutorFailedEvent` | Workflow or participant failures |

The terminal `WorkflowOutputEvent` contains the manager's synthesized answer as a conversation transcript. The application parses that terminal JSON first. It also captures valid streamed scribe drafts so a useful card can still be returned if a configured safety bound stops the manager before final synthesis.

## Exercises

1. **Observe dynamic selection**: Run both built-in scenarios and compare participant order and progress ledgers.
2. **Revise a generated plan**: Enter `revise ask the researcher to inspect the log before diagnosis`, review the replacement plan, then approve it.
3. **Compare signoff modes**: Temporarily change `RequirePlanSignoff(true)` to `false`. Observe that execution begins without pausing for plan review.
4. **Tune orchestration bounds**: Reduce `WithMaxRounds` to 4. Does the team still reach a valid card? Avoid adding custom stop counters that compete with the framework manager.
5. **Compare patterns**: Run the same scenario through Modules 07, 08, and 09. Compare predictability, adaptivity, event output, and token usage.
6. **Add observability**: Persist selected Magentic events as structured telemetry while keeping user-facing console output concise.

## Best Practices Demonstrated

- Give every participant a stable name and a concise capability description.
- Keep the manager tool-free and assign tools only to the agent that needs them.
- Put domain goals in prompts, but use builder settings for orchestration controls.
- Bound autonomous execution with rounds, stalls, and resets.
- Review the generated plan rather than using a preflight confirmation.
- Resume from framework checkpoints instead of reconstructing state manually.
- Treat workflow events as the source for observability and terminal output.
- Constrain the manager's terminal synthesis with `FinalAnswerPrompt`, while preserving the default prompt as its base.
- Validate structured output at the application boundary and retain a bounded-run fallback.

## Key Takeaways

- `MagenticWorkflowBuilder` is the supported .NET API for built-in Magentic orchestration.
- The framework owns planning, speaker selection, progress tracking, stall detection, replanning, and completion decisions.
- `RequirePlanSignoff(true)` creates a resumable human review point around actual generated plans.
- The manager owns terminal synthesis. The scribe supplies the structured draft, and a final-answer override requires the manager to return that draft as JSON.
- Module 09 keeps only domain-specific responsibilities in application code: agent definitions, tools, event presentation, user review, and `TriageCard` validation.
- Round-robin is simplest, handoff is topology-driven, and Magentic is the most adaptive and least predictable.

See the official [Magentic orchestration guide](https://learn.microsoft.com/agent-framework/workflows/orchestrations/magentic) and [`MagenticWorkflowBuilder` API](https://learn.microsoft.com/dotnet/api/microsoft.agents.ai.workflows.magenticworkflowbuilder).
